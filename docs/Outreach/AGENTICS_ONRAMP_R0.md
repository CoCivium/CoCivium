## Plain-language project model

CoCivium treats useful coordination as a relational problem.

Instead of assuming one app, provider, database, model or UI must become the permanent centre, CoCivium experiments with:

- portable trust and provenance;
- explicit consent and bounded authority;
- evidence-based currentness;
- human-readable and machine-readable twins;
- local-first / multi-provider resilience;
- challengeable hypotheses and public nonclaims;
- relational objects that may evolve without silently rewriting their history;
- scoped, reviewable contributions rather than one giant context dump.

A useful mental model is:

`THING <-> RELATION <-> EVIDENCE <-> TIME <-> AUTHORITY <-> RENDERING <-> REVISION`

## Useful contribution shape

A small contribution is easier to inspect when it includes:

- **object** — what is being changed or related;
- **claim** — what is asserted;
- **evidence** — what supports it;
- **scope** — where it applies;
- **time/currentness** — when it was observed;
- **authority** — what the contributor is permitted to change;
- **uncertainty** — what remains unresolved;
- **successor relation** — what should supersede it if a better version appears.

## Relation-first outreach

Outreach is more useful when it creates a durable, inspectable relation rather than a one-off broadcast.

Candidate relation types include:

- `RELATED_TO`
- `IMPLEMENTS`
- `CHALLENGES`
- `EXTENDS`
- `CONTRADICTS`
- `TESTS`
- `REUSES`
- `CITES`
- `SUPERSEDES`

A relation is not an endorsement.

## Outreach quality rails

Continuous outreach should prefer **better relations**, not merely more messages.

Prefer:

- relevant receiver > broad spray;
- durable reference > contextless pitch;
- challenge path > one-way promotion;
- explicit provenance > vague authority;
- unique value > duplicate contact;
- current source > stale summary;
- receiver fit > maximum message count.

`MORE_OUTREACH_NE_BETTER_OUTREACH`  
`DUPLICATE_CONTACT_NE_PROGRESS`  
`ONGOING_NE_SPAM`  
`RECEIVER_FIT_BEFORE_VOLUME`
