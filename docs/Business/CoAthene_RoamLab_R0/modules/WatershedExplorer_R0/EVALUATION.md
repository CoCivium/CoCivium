# Evaluation Contract — Watershed Explorer R0

The module should be evaluated against learning and operating evidence, not headset novelty.

## Learner-level evidence

Collect only what is necessary and preferably without persistent identity.

A facilitator may score a team's before/after response using a 0-2 rubric:

### Evidence-type distinction

- 0: conflates model observations, world observations, source statements and inference.
- 1: distinguishes some types but still overgeneralizes.
- 2: consistently distinguishes model observation, world observation, source statement and inference in the final explanation.

### Causal explanation

- 0: unsupported slogan or disconnected facts.
- 1: plausible relation chain with gaps.
- 2: plausible relation chain tied to model observations and source evidence.

### Uncertainty

- 0: claims certainty or leaves blank.
- 1: names a generic uncertainty.
- 2: names a specific uncertainty linked to the explanation.

### Next measurement

- 0: irrelevant or absent.
- 1: relevant but not clearly tied to uncertainty.
- 2: measurement directly reduces a named uncertainty.

Maximum: 8 points.

This score is for module evaluation and formative teaching only. It is not a psychological profile or high-stakes learner ranking.

## Module-level evidence

Track:

- setup minutes;
- teardown minutes;
- facilitator count;
- participant count;
- equipment failure count;
- number choosing non-headset path;
- motion/discomfort stops if immersive mode used;
- completion rate;
- teacher/facilitator usefulness rating;
- before/after rubric change at aggregate level;
- recurring confusion points;
- accessibility failures;
- privacy/safety incidents.

## Comparison test

Where possible, compare:

A. physical/source lesson only  
B. physical/source lesson + immersive visualization

Do not assume B wins.

Useful comparison dimensions:

- learning gain;
- time cost;
- facilitator load;
- accessibility;
- discomfort;
- equipment failures;
- learner engagement;
- cost per learner.

## Success gate

A future R1 should require evidence that the module:

- improves at least one target learning dimension;
- does not depend on persistent learner profiling;
- retains a meaningful non-headset path;
- is operationally feasible inside school/session time;
- can recover from device/network failure;
- can run from a dated offline source pack when internet access disappears;
- preserves the same core objective for non-headset learners;
- produces a correction backlog from observed failures.

## Negative knowledge

Publish material failures such as:

- confusing simulation labels;
- false causal inferences;
- inaccessible interactions;
- excessive setup time;
- device overheating/battery issues;
- motion discomfort;
- network dependency;
- source staleness.

## R0A synthetic dry-run gate

Before a real pilot, the package must also pass the machine-readable failure scenarios in `DRY_RUN_SCENARIOS.json`.

This validates declared fallback coverage only. It does not simulate human learning accurately and does not replace educator review.
