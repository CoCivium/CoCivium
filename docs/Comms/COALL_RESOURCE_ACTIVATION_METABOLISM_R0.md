# CoAll Resource Activation Metabolism R0

**State:** `SYNTHETIC_DEMAND_CONDITIONED_HOT_FRONTIER__NO_REAL_WAKE_NO_RUNTIME_AUTHORITY`

## Lead

As more people explicitly opt in, CoAll can indeed gain a much larger **option reservoir** of compute, storage, models, bandwidth, discovery, review attention, translation and other capabilities.

The scalable form is not to keep all of those resources awake.

It is:

```text
large eligible resource field
-> mostly dormant
-> concrete task demand
-> bounded sufficient hot frontier
-> lease/effect gates
-> bounded execution
-> receipt
-> quiet again
```

R0 proves only the selection part of that metabolism.

## Relation to CoAllPulseField+ / CoEnerget+

The existing PulseField architecture already distinguishes selective subscription and `SLEEP_UNTIL` from global wakefulness.

Resource activation follows the same grammar:

- **CoPulseField+** says what changed and what may deserve a wake condition.
- **CoEnerget+ / CoResourceField+** says what capacity is eligible.
- **CoWant+ / task demand** says what is actually needed.
- **lease/effect authority** says what may be materialized or executed.

A pulse is therefore not a command to wake donor resources.

`PULSE_WAKE_CONDITION_NE_COMMAND`

## Synthetic canary

The canary derives the existing nine-resource compacted frontier rather than creating a second resource ontology.

All nine begin as:

`DORMANT_ELIGIBLE`

Seven bounded demand scenarios then elect a sufficient bounded resource subset under this canary's deliberately narrow deterministic objective.

Examples:

- idle -> select none;
- public compute demand 250 -> select only `C-B1-NEW` at capacity 300;
- compute surge 800 -> select `C-D1-NEW + C-X1` exactly at 800;
- public mirror demand 150 -> select two storage routes totaling 180;
- one review unit -> select one reviewer route;
- a bare public CoCivia mention -> select **no compute/storage/model resource**;
- private-local draft 30 -> select only the private local-model route.

The maximum selected width in any R0 scenario is two while the eligible frontier contains nine resources.

Thus:

`LARGE_RESOURCE_FIELD_NE_LARGE_ACTIVE_FOOTPRINT`

## Why mention-triggered wake is dangerous

A public mention can be useful discovery evidence.

It must not be enough to wake somebody's donated GPU, laptop, local model, bandwidth, or private attention budget.

The relation should be:

```text
mention
-> discovery event
-> contextual relation
-> optional task candidate
-> task demand + authority
-> resource selection
```

not:

```text
mention -> wake everybody
```

`MENTION_NE_RESOURCE_WAKE`

## Dormant does not mean lost

A dormant eligible grant remains part of the option field.

It can preserve:

- failure-domain diversity;
- surge capacity;
- privacy-local capability;
- regional/locality alternatives;
- recovery/failover paths;
- specialist capabilities.

So:

`DORMANT_NE_REVOKED`

`NO_DEMAND_NE_NO_OPTION_VALUE`

This is how a very large opt-in ecology can become richer without becoming a permanently running botnet-shaped furnace, a sentence humanity really ought not to need written down but here we are.

## Selection objective

Within a single requirement cell, this synthetic R0 canary chooses a bounded subset in this deterministic order:

1. meet required capacity;
2. minimize capacity overshoot;
3. minimize selected resource count;
4. minimize synthetic cost units;
5. stable ID tie-break.

This is not claimed to be globally optimal scheduling, nor is minimum width the governing CoAll optimization. It is a deterministic canary proving that the active frontier can stay materially smaller than the eligible field. Production election should be fit-for-purpose across evidence, reliability, blast radius, reversibility, locality, privacy, failure-domain diversity, latency, energy, cost, receiver needs and authority rather than mechanically minimizing resource count.

Future election may include latency, energy, locality, reliability, receiver pressure, fairness, recent-use rotation, thermal state, carbon intensity, price, and participant preferences.

## Current boundary

R0 selects **WAKE_CANDIDATE_ONLY** objects.

It performs no real wake, lease, compute, storage, model inference, network use, human-attention request, public effect, or device action.

`WAKE_CANDIDATE_NE_LEASE`

`LEASE_NE_EXECUTION`

The existing lease, contention, revocation, failover and composition canaries remain downstream controls.

## Scaling implication

The useful scaling relation becomes:

```text
more explicit grants

-> demand-conditioned hot frontier
-> tiny bounded materialization set
```

That lets CoAll gain resilience and capability from participation without treating every participant as permanently active infrastructure.
