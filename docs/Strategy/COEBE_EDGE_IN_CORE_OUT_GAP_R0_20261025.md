## Working terms and why they matter

[CoEvo March 24 source](../CoEvo/CoEvo_Megascroller_v0__2026-03-24.md) expressly defines **CoEBE = CoEvolutionary Edge-Balanced Equilibrium**: adaptive trust without a dominating actor. The shorthand **Edge Balance Equilibrium** is also used in prior work.

**CCC = Core Controlled Coercion** describes how indispensable centralized resources, meanings, identity and permissions can capture participants. **CoCCC / CoCoreControlledCoercion** is a historical diagnostic emphasis on the same concentrated-control danger, not evidence of a new external organization or a separately ratified specification. The opposite danger, **ECC = Edge Controlled Coercion**, describes multiple restrictive little cores: decentralization without interoperability, rights or real exit is not necessarily equilibrium.

**Core-out**: invent protocols → build demos → verify source → publish → hope the edge comes.  
**Edge-in**: discover a voluntary real need → enable one successful task → respect the participant's ownership and exit → accept correction → improve common protocols.

Neither approach should monopolize the other. CoEBE means a competent, replaceable core and sufficiently autonomous, interoperable edges.

## CoCoopetition+ acceptance, not another volume contest

| Relation | Core-only indicator | Evidence needed at the edge |
| --- | --- | --- |
| Discovery | A repository or URL exists | Two outside networks load one correct, reviewed, useful human entry |
| Understandability | A detailed manifesto exists | Unfamiliar consenting visitor explains what to try |
| First benefit | A synthetic demonstration passes | One real person completes a task, then a five-person pilot with failures |
| Reciprocity | Sent emails, issue comments or API readbacks | An independent correction/reuse/return with a real receipt |
| Portable agency | Multiple models or accounts are configured | One person leaves/forks without a captive central account |
| Survival | Multiple copies under one provider | A separate custodian restores and uses a pinned public-safe artifact |

### CoInversion+ tests

- **Start at the edge:** Give one outsider a real task; don't lead with CoAll vocabulary. If comprehension doesn't improve relative to the existing first-use page, revise or stop.
- **Remove the core:** Demonstrate a useful offline artifact without X2, GitHub or ChatGPT. Receiver-produced exact hash and task result are required.
- **Remove the brand:** Try the same useful first task with plain language rather than project names. This measures utility, not branding prejudice.
- **Remove the account:** Verify a no-login user can finish, correct and export work without surrendering identity or relying on hidden synchronization.
- **Turn the arrow around:** The edge's criticism should produce a dated accepted/rejected change with a reason, source diff and recovery trail.
- **Try a null baseline:** If an ordinary link to the GitHub first-use page gives the same outcome as an elaborate new specialist, do not spend resources constructing another branded door.

No randomized study or edge-user pilot is claimed. One independent task receipt, then five consenting participants, is the proposed small progression. Source checks, stars, followers and generation speed are **not** equivalent to independent benefit.

## Rebalancing principle

`CORE_INVENTION -> SOURCE_PROOF -> PUBLIC_POINTER` **does not imply** `INDEPENDENT_DISCOVERY -> FIRST_USE -> RETURN -> REUSE -> INDEPENDENT_STEWARDSHIP`.

CoEBE works when the reverse flow also exists:

`EDGE_NEED -> SIMPLE_TASK -> OBSERVED_BENEFIT -> CHALLENGE -> SHARED_PROTOCOL_IMPROVEMENT -> EDGE_FORK/EXIT`.

**What could falsify the headline hypothesis?** A safe, accessible and independently reachable front door plus repeat outsider success that still fails to generate interest would push inquiry toward product value, audience relevance, incentives or distribution rather than assuming core/edge routing is the main cause.
