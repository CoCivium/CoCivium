## Thesis

Long-running logjams may be caused not only by missing capability, but by what the system already carries: anchors, stale plans, duplicated structures, inherited constraints, provider dependencies, drift controls, unretired artifacts, and assumptions embedded in prior architectures.

Therefore optimization should inspect both:

`WHAT_IS_MISSING`
and
`WHAT_PRESENT_STRUCTURE_IS_BLOCKING_FLOW`

## Anchor classes

### 1. Enabling anchors
Preserve identity and trust while allowing change.

Examples:
- provenance;
- consent;
- authority boundaries;
- currentness;
- receipts;
- reversibility;
- recovery;
- source lineage;
- privacy;
- explicit uncertainty.

These should usually remain stable enough to support safe flow.

### 2. Drag anchors
Structures that once helped but now reduce useful movement.

Examples:
- stale provider-specific recurrence;
- founder relay;
- duplicate ontologies;
- unowned plans;
- obsolete interfaces;
- manually repeated continuity packets;
- hidden single-home dependencies;
- frozen publication structures;
- legacy assumptions copied into new substrates.

### 3. False anchors
Things treated as necessary without evidence they are still necessary.

Examples:
- 'this must remain centralized';
- 'this must run continuously';
- 'this term must stay canonical';
- 'this provider is required';
- 'this workflow needs Rick';
- 'stability is always safer';
- 'change is always better'.

### 4. Dynamic anchors
Constraints allowed to move as evidence changes.

Examples:
- preferred model;
- active receiver;
- current product surface;
- routing;
- scheduling;
- resource allocation;
- publication emphasis.

## Drift relation

Drift can be harmful, neutral, or adaptive.

Track:
`DRIFT_SOURCE`
`DRIFT_RATE`
`DRIFT_DIRECTION`
`DRIFT_COST`
`DRIFT_BENEFIT`
`RECOVERY_OR_SUCCESSION_PATH`

Do not optimize for zero drift.

`ZERO_DRIFT_NE_HEALTH`

Some systems need:
- bounded drift;
- exploratory drift;
- phase shifts;
- succession;
- branch escape;
- return to invariant;
- convergence after useful divergence.

## Delta mining

Compare what repeatedly worked against what repeatedly stalled.

### Worked / promising pattern families
- source-bound receipts;
- bounded reversible canaries;
- explicit uncertainty;
- source-to-successor lineage;
- local-first / FOSS-capable paths;
- visual/currentness separation;
- publication that actually reached a public surface;
- media generation with explicit internal-review state;
- failure preservation;
- lazy generation rather than eager ontology;
- receiver-relative projections;
- independent challenge routes.

### Repeatedly stalled / weak pattern families
- X2 remote-observer continuity;
- provider-owned recurrence;
- founder/Rick state relay;
- many concepts without receiver pickup;
- article/output creation without independent audience return;
- speculative scale claims without time series;
- repeated rediscovery;
- parallel fan-out without fan-in;
- currentness drift across surfaces;
- overly broad 'always on' assumptions.

## Inspiration from the delta

The difference between worked and stalled patterns suggests design rules:

1. Prefer source-bound state over remembered state.
2. Prefer bounded canaries over broad activation.
3. Prefer reusable capabilities over recurring prompts.
4. Prefer receiver closure over artifact count.
5. Prefer independent replay over confidence.
6. Prefer successor lineage over silent mutation.
7. Prefer local/open fallback over single-provider dependence.
8. Prefer wake-on-delta over always-running loops.
9. Prefer many candidate models but tiny elected action fronts.
10. Prefer explicit retirement over indefinite accumulation.

## Discover / rediscover / undiscover

Three distinct operations:

### Discover
Surface a relation not currently represented.

### Rediscover
Recover useful prior structure that became dormant, stale, fragmented, or forgotten.

### Undiscover
Deliberately de-privilege a claimed discovery that no longer survives evidence, usefulness, receiver need, or contradiction.

`UNDISCOVER_NE_DELETE_HISTORY`

Undiscovery preserves lineage while removing unjustified privilege.

## CoFlow audit

For every major asset / recurrence / architecture / plan:

Ask:
1. Does it increase useful flow?
2. Does it reduce future option space?
3. Does it require human relay?
4. Does it depend on one provider?
5. Does it have a receiver?
6. Does it have a wake rule?
7. Does it have a stop / retire / successor rule?
8. Is it an enabling anchor or drag anchor?
9. What happens if removed?
10. What happens if loosened?
11. What happens if inverted?
12. What does the worked-vs-stalled delta suggest?
