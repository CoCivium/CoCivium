## Purpose

Establish one shared, iterative evolution workflow across CoCivium artifacts, authorized sessions and contributors, email drafts, publication work, and other connected surfaces. The workflow is designed to reduce manual thread-chasing without claiming that all sessions are currently connected or synchronized.

4. **Contribution/review queue:** proposed changes, questions, source requests, disagreements, approvals, and next actions.
5. **Publication ledger:** candidate outputs, evidence and citation checks, intended venue, review deadlines, submission status, and publication receipts.
6. **Other workspaces:** connect only when an available, authorized integration is confirmed; record which source is authoritative and what synchronization does or does not cover.

## Shared evolution packet

Each contribution should carry:
- stable artifact/task ID and source/version references;
- proposed change and rationale;
- evidence/citations and uncertainty;
- alternatives, counterarguments, and unresolved questions;
- author/contributor and attribution preference;
- privacy/sharing scope and required permissions;
- review/acceptance criteria and next action;
- outcome receipt and successor version.

Contributions can be suggestions, patches, critiques, references, tests, or finished artifacts. Participation is optional; no agent or session is presumed to have received this directive until a delivery path and receipt are confirmed.

## Iteration protocol

1. Discover existing source and current versions before creating duplicates.
2. Propose bounded changes against a named source.
3. Compare alternatives and retain substantive disagreement.
4. Verify citations and distinguish influence from analogy or independent convergence.
5. Review privacy, consent, authority, attribution, and external claims.
6. Accept, revise, defer, or reject with a reason.
7. Publish a new version with a change note and source pointers.
8. Update authorized projections individually and record each result.
9. Preserve unresolved tasks with an owner or unassigned status and a next wake/check.
10. Mark completion only when observable acceptance criteria are satisfied.
