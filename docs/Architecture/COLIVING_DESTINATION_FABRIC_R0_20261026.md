# CoLivingDestination+ Fabric R0

**State:** CANDIDATE_SHARED_PRIMITIVE__NOT_HOSTED_RUNTIME__NOT_AUTO_PUBLISH__NOT_DELIVERY_PROOF
**Observed:** 2026-10-26

## Thesis

Many CoCivium surfaces need the same underlying capability:

`IMMUTABLE_EVENT / SNAPSHOT -> STABLE_IDENTITY -> VERSIONED_LIVING_RESOURCE -> RECIPIENT_CONTROL -> CHALLENGE -> SUCCESSOR -> ARCHIVE`

Do not reimplement this separately for email, articles, books, media, CoOrb, outreach packets, invitations, or dashboards.

## Surfaces

- CoMail;
- Substack/publication;
- CoBook;
- CoVids / rich media;
- CoOrb / CoMap projections;
- outreach packets;
- invitations / agendas;
- research briefs;
- public dashboards;
- machine-readable manifests;
- academic/community discussion packets.

## Event vs destination

An event remains historical:
- what was sent;
- what was published;
- what was shown;
- what was agreed;
- what was cited;
- when and to whom.

A living destination may evolve:
- corrections;
- clarifications;
- new evidence;
- successors;
- translations;
- accessibility versions;
- media twins;
- challenge responses;
- retirement / tombstone.

`EVENT_NE_DESTINATION`
`SNAPSHOT_NE_CURRENT_VERSION`

## Recipient sovereignty

Every receiver should be able to:
- pin original;
- follow current;
- pause updates;
- compare versions;
- export a readable copy;
- inspect provenance;
- challenge or propose correction;
- leave / unsubscribe where applicable.

`FOLLOW_NE_FORCED_UPDATE`

## Current pointer

Each living object gets:
- stable object identity;
- immutable version IDs;
- predecessor/successor links;
- current pointer;
- evidence/currentness state;
- change summary;
- source/authorship state;
- authority boundary;
- privacy class;
- optional receiver-specific projection.

## Cross-surface projection

One living object can project as:
- email link;
- web page;
- CoOrb card;
- CoMap node;
- RSS/Atom item;
- PDF/print snapshot;
- audio/video edition;
- machine JSON;
- accessible low-bandwidth view.

`MANY_PROJECTIONS_NE_MANY_TRUTH_STORES`

## Auto-evolution policy

Allowed automatically only for low-risk derived projections where source and rules permit:
- formatting;
- accessibility transforms;
- translations marked with provenance;
- generated summaries;
- currentness labels;
- successor pointers;
- machine indexes.

Material semantic changes require source-bound review and version creation.

`AUTO_EVO_NE_SILENT_SEMANTIC_MUTATION`

## Fame / community / feedback

Community participation may attach:
- corrections;
- counterexamples;
- implementations;
- replications;
- translations;
- remix proposals;
- accessibility fixes;
- contributor credit;
- optional recognition.

Popularity, fame, donations, or engagement never change evidence rank.

`FAME_NE_TRUTH`
`FEEDBACK_NE_ADOPTION`

## G_d / mythic lane

G_d-oriented material may live as a marked philosophical/hypothesis projection with preserved alternatives and challenge paths.

`GD_PROJECTION_NE_GD_PROOF`

## CoCopy / CoAckRewise relation

Every material version delta can emit a local continuity event:

`OBJECT_UPDATED -> SOURCE_DELTA -> REVIEW_STATE -> CURRENT_POINTER -> ACK/REWISE -> RECEIVER_RETURN`

CoCopy stores the human-scale temporal trace; CoMap stores relation topology.

## CoZillion relation

Do not create a new object for every combination.

Generate receiver/time/substrate projections lazily from one source identity.

`ZILLION_PROJECTIONS_ADDRESSABLE_NE_ZILLION_OBJECTS_ACTIVE`

## First proof

Take one existing CoMail capsule and one existing public article.

Prove both can use the same generic living-destination schema for:
1. identity;
2. immutable history;
3. current pointer;
4. version compare;
5. challenge;
6. recipient preference;
7. export;
8. successor;
9. archive/tombstone.

Pass only if the schema preserves each surface's historical event and does not imply delivery, read, consent, or adoption.
