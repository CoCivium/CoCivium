# CoPromptEcology+ / CoAlwaysEcology+ R0

**State:** `CANDIDATE__DRAFT_PR__NO_CANON_RUNTIME_OR_AUTHORITY_CHANGE`

## Lead

CoCivium should treat continual prompting as a **typed relational ecology**, not as one immortal instruction loop.

The purpose is to keep meaningful priors, relations, wake conditions, challenges, successor paths and bounded evolution **continually eligible for reconsideration** without implying that everything must remain physically active.

`ALWAYS_ALIVE_TO_RELEVANCE_NE_ALWAYS_RUNNING`
`PROMPT_NE_COMMAND_NE_AUTHORITY`
`RECURSIVE_IMPROVEMENT_NE_SELF_AUTHORITY`

## Base loop

`PULSE -> CURRENTNESS_CHECK -> SELECT_PROMPT_SET -> GENERATE_BOUNDED_CANDIDATES -> DEDUPE -> CHALLENGE -> VERIFY -> COOOMPH_PACE -> ROUTE -> RECEIPT -> DORMANT_OR_WAKE`

This loop composes existing CoSessionAutocycle+, CoSubscriptionEcology+, CoEvidenceReceiptGuard+, CoOomph+ pacing and the shared CoAll evolution fabric.

## Continual prompt families

### CoObservePrompt+
What materially changed since the last proven state?

### CoPriorPrompt+
Which old priors, relations, dormant artifacts, unresolved negatives or superseded objects have become relevant again?

### CoRelPrompt+
What new relation, relation-of-relations, contradiction, dependency, optionality or receiver relation can now be proposed or tested?

### CoEvoPrompt+
What bounded change would improve this object or its surrounding relation field?

### CoAutoEvoPrompt+
Which safe candidate improvements can be observed, compared, simulated, proposed, challenged or verified without human relay?

### CoOomphPrompt+
Where should effort accelerate, compact, sleep, fan out, serialize or stop based on marginal verified value and receiver capacity?

### CoChallengePrompt+
Which assumption is weakest, stale, circular, self-confirming, under-sourced or missing an independent challenger?

### CoTurtlePrompt+
What rule governs this relation, what governs that rule, and can recursion be collapsed into a reusable invariant rather than another controller?

### CoWakePrompt+
Which dormant relation now has a materially satisfied wake condition?

### CoSuccessorPrompt+
What should supersede this state, and what lineage must remain recoverable?

### CoReceiverPrompt+
Who or what actually receives, benefits, verifies, challenges, rejects, adopts or acts on this delta?

### CoMetaPrompt+
Which prompt rules themselves need changing, splitting, combining, retiring, dormancy or evolution?

## Multi-speed cadence

Continual does not mean uniform cadence.

- `EVENT` — contradiction, new source, receiver response, failure, capability change.
- `FAST` — currentness, pressure, stale-state, route health.
- `MEDIUM` — unresolved priors, successor gaps, outreach relevance.
- `SLOW` — ontology drift, duplicate concepts, deep prior resurrection.
- `WAKE_ONLY` — expensive research, dormant projects, effectful external work.
- `ON_DEMAND` — receiver-specific projection or explanation.

`CADENCE_NE_IMPORTANCE`
`NO_CHANGE_CAN_BE_VALID_OUTPUT`

## Turtle envelope

Every control relation should itself be representable as a relation object carrying:

`identity | purpose | scope | evidence | authority | cadence | wake_conditions | inputs | outputs | receiver | successor | supersedes | confidence | cost | cooomph_policy | provenance | currentness`

This lets prompt rules, evolution rules and pacing rules evolve under the same evidence-bearing lineage model instead of spawning an infinite tower of special controllers.

`TURTLES_AS_REUSABLE_SCHEMA_NE_INFINITE_DAEMONS`

## Prompt selection

Do not run every prompt against every object.

Candidate selection score:

`expected_verified_relation_gain * relevance * novelty * receiver_fit * optionality / (cost + duplication + proof_debt + receiver_pressure + collision_risk)`

The score is only a prioritization aid.

`SCORE_NE_TRUTH`
`HIGH_SCORE_NE_AUTHORITY`

## Evidence and receipts

Any claimed progress produced by this ecology must obey CoEvidenceReceiptGuard+.

Prefer:

- no progress claim over false success;
- fresh evidence from the exact output;
- explicit uncertainty;
- producer receipt separate from receiver pickup;
- bounded lineage and successor pointers.

`NO_RECEIPT_IS_BETTER_THAN_FALSE_RECEIPT`
`PRODUCER_RECEIPT_NE_RECEIVER_PICKUP`

## Prior-estate conversion

Do not reopen old sessions merely to make them "always."

Prefer:

`old artifact/session/relation -> extract durable meaning -> classify always modes -> bind wake predicates -> bind successor/currentness -> source embodiment may remain closed`

`OUTLIVE_EMBODIMENT_NE_RUN_FOREVER`
`SESSION_NE_WORK`

## Future-signal questions

Each bounded cycle SHOULD consider:

1. What did we fail to ask?
2. What prior now matters?
3. What relation is missing?
4. What relation is wrong?
5. What relation should sleep?

7. What controller can be removed by a better invariant?
8. What new future signal should be bound now?
